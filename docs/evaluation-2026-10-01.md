# dsh-plugin-manager 系统全面评估报告

- **评估对象**：`@2768651338/dsh-plugin-manager` v0.7.0（DSH 插件管家）
- **评估日期**：2026-10-01
- **评估方法**：全量精读 `src/` 全部源码（主机半、浏览器半、typert 工件、补丁编辑、备份、目录，约 2500 行）、构建配置（`tsdown.config.ts` / `platform.ts`）、部署补丁（`cordis.patch.yml`）、README/CHANGELOG；实跑 `pnpm typecheck` 与全部 5 个测试套件；结合 e2e 实际输出核对其中的行为。
- **验证结果基线**：typecheck 通过；`patch-file` 冒烟 9/9、`backup` 冒烟 7 组、`claims` / `gateway-path` / `host-gateway` 三套 e2e 在 0.2.0-rc.2 与 0.1.5-rc.3 双宿主下全部通过。

## 0. 关于"预约流程"的说明

本系统不存在预约流程。评估目标中列举的"预约流程的便捷性"按最接近的对应物执行：**插件启停写流程**（点开关 → 改写 `cordis.patch.yml` → 热加载）与**备份导入/恢复流程**（选文件 → 合并写入三个文件 → 提示手动安装），外加安装命令路径（`dsh plugin add`）。这两个写流程正是本系统风险最集中的地方，下文 P0/P1 项大多落在这里。

## 1. 总体结论

这是一个工程质量明显高于社区平均水平的单插件：手术式补丁编辑、`!!js` 表达式保护、系统行保护、备份版本校验、双宿主（0.1.x / 0.2.0）codec 兼容、客户端 bundle 纯度守卫、密封式 e2e 测试，都做得扎实。

主要短板集中在两处：

1. **写文件的防呆兜底不足**——三处直接 `writeFileSync` 非原子写、改写前无自动备份、写后无 YAML 语义校验、备份导入"即选即写"无预览。任何一个环节出意外（崩溃、断电、坏备份文件），后果都是配置损坏或意外安装代码，且不可逆。
2. **工程化缺失**——无 lint、无 CI，浏览器半无测试，两份 typert 工件全量重复，长期演进时容易在无声处腐烂。

安全方面，网关方法无自有鉴权、完全依赖宿主信任栅栏，且备份导入存在一条"导入 → 写依赖 → 用户手动 install → 执行任意代码"的供应链路径，需要收敛。

### P0-1 补丁/配置写入非原子，改写前无自动备份

**问题**：`src/index.ts:357`（补丁文件）、`src/index.ts:192`（catalog.json）、`src/index.ts:143`（profile package.json）都是直接 `writeFileSync` 覆盖写。进程在写入中途被杀、断电或磁盘满，文件就会处于截断/半截状态；`cordis.patch.yml` 又被宿主 HMR 观察者实时监听，写坏了立刻被热加载。另外全系统没有任何一份"改写前"的备份。

**建议**：三处写全部改为"临时文件 + rename"原子替换；每天第一次改写 `cordis.patch.yml` 前自动复制一份带时间戳的 `.bak`（保留最近 3-5 份，滚动清理）。

**难度**：低（node `fs.renameSync` 同目录原子；备份逻辑约 30 行）。

- **为什么这么定级**：概率低但后果不可逆——其它 P1/P2 项坏了顶多体验差，这一项坏了是"整个启停体系失效、可能连应用都起不来"，而修复成本不到半天。定级看的是"后果 × 成本"，不是概率。
- **一句话版本**：写配置文件必须先落临时文件再原子替换，动它之前先留后路。
- **一个需要知道的取舍**：临时文件 + rename 在 Windows 上目标被占用（编辑器/杀毒软件锁定）时会抛错，需要捕获后降级为直接写并提示，而不是让启停彻底失败；`.bak` 文件会占一点磁盘且含用户备注，注意滚动清理。
- **事故是怎么发生的**：用户点停用的瞬间 Windows 更新强制重启（或杀毒软件恰好扫描锁定文件）→ `writeFileSync` 写了一半 → HMR 观察者读到半截 YAML → 配置解析失败，所有插件的启停状态丢失，用户看到的是"应用坏了"，而他没有能力手工恢复一个截断的 YAML。

### P0-2 补丁写入无 YAML 回读校验

**问题**：`src/patch-file.ts` 是手写的行级 YAML 编辑器，能正确处理启动器生成的标准格式，但有三类它管不到的输入：`id` 不是行块首键的行（如 `- name: x` 换行 `id: y`）会被当作"无 id"，启用/停用时静默**追加一个重复行**，永远不生效也不报错；`disabled: true # 注释` 这类行内注释在改写时被整行替换销毁（`src/patch-file.ts:130,147`）；顶层不是数组的手写 YAML 被 `appendRow` 直接在文件尾追加数组行，产出非法 YAML。写完没有"回读解析确认仍是合法 YAML"的兜底。

**建议**：在 `setEnabled` / `importBackup` 写盘前，把编辑后的内容用 `js-yaml` parse 一次（js-yaml 已在 devDependencies，提为运行时依赖即可），parse 失败就拒绝写入并返回明确错误；对"目标行存在但本插件识别不出 id"的情况返回"行格式无法识别"而不是静默追加。

**难度**：低-中（parse 一行代码；把 js-yaml 提为运行时依赖 + 错误文案 + 测试）。

- **为什么这么定级**：它是 P0-1 的姊妹项——P0-1 防的是"物理写坏"，这一项防的是"逻辑写坏"（文件合法但语义错了/新写进去的内容非法）。用户手工编辑过的补丁文件是真实存在的使用方式（README 明确支持），触发概率不低。
- **一句话版本**：自己改完的 YAML，必须机器重新解析确认合法才允许落盘。
- **一个需要知道的取舍**：引入 js-yaml 运行时依赖会让发布包多一个依赖（宿主 profile 的 node_modules 需要能解析到它）；也可以用更轻的"行块结构自检"替代，但自检的覆盖面永远追不上真解析器。建议直接加依赖——主机半本来就跑在完整 node 环境里。
- **事故是怎么发生的**：用户按自己的习惯把 `- id: foo` 写成多行形式（合法 YAML），之后在界面里点"停用"→ 插件没认出这行，往文件尾追加了一个新的 `- id: foo / disabled: true` → 界面显示"已提交，正在热加载"，实际什么也没发生；或者用户把顶层改成了映射结构，一次启停直接产出非法 YAML → 热加载报错，整个补丁层失效。

### P0-3 备份导入可写入任意依赖 spec（供应链面）

**问题**：`importBackup`（`src/index.ts:398`）对 `dependencies` 只校验"值是字符串"（`src/backup.ts:55`），不校验 spec 语义，就合并进 `<profile>/package.json` 并提示用户执行 `dsh plugin --profile web install`。一份恶意或被调包的备份文件可以把依赖指向任意 git 仓库 / 本地路径 / 非官方 registry，用户按提示一跑安装命令就执行了攻击者选定的代码。`json` 参数本身也没有大小上限。

**建议**：默认只接受 registry 风格的 spec（版本号 / 版本范围 / npm dist-tag）；遇到 `git:`、`file:`、`http(s)://`、GitHub shorthand 等非常规 spec 时，不接受静默合并——把逐条清单返回给界面，要求用户逐项勾选确认后才写入；同时给 `json` 参数加一个合理的大小上限（如 2MB）。

**难度**：低-中（spec 分类函数 + 确认交互；主机侧先返回"待确认清单"改动接口形状）。

- **为什么这么定级**：这是全系统唯一一条"一个文件就能让用户主动执行任意代码"的路径。利用前提是攻击者能诱导用户导入一份文件（社交工程），门槛不低，但后果是完整的主机代码执行，且现有校验给用户的是虚假安全感——界面明明白白写着"恢复完成"。
- **一句话版本**：导入备份时，"从哪儿装代码"的决定必须由用户逐条看过，不能由备份文件替他做。
- **一个需要知道的取舍**：严格 spec 白名单会挡住当前真实存在的合法用法——profile 依赖本来就支持 git/file 安装（README 安装命令就在用 `github:` 形式），所以不能一刀切禁止，只能"默认拦 + 显式确认放行"，这会让导入流程多一步，需要在 UI 上把"为什么要多点一下"解释清楚。
- **事故是怎么发生的**：用户在群里拿到一份" fellow 用户分享的插件清单备份"导入 → 备份里 `@deepseek-ai/dsh-llm` 的 spec 指向一个同名 fork 仓库 → 界面提示"恢复完成，请运行 install"→ 用户照做 → install 拉取并执行了 fork 里的代码，而整个过程界面没有任何警告。

### P1-1 三条独立写队列，导入与启停并发丢更新

**问题**：主机网关有三条互不感知的串行队列：`toggleQueue`（`src/index.ts:157`）、`overrideQueue`（`src/index.ts:184`）、`restoreQueue`（`src/index.ts:187`）。`importBackup` 在 restoreQueue 里连写三个文件，`setEnabled` 在 toggleQueue 里写同一个补丁文件，`setOverride` 在 overrideQueue 里写同一个 catalog.json——两个操作并发时（导入进行中用户点了开关），后写的覆盖先写的，丢失更新。`setEnabled` 里的写前重读只防"外部手工编辑"，防不住插件内部的队列间竞争。

**建议**：三条队列合并为一条全局写队列（所有落盘方法共用），或按文件分队列但补丁文件、catalog.json 的写入方全部走各自那条。改动是机械的。

**难度**：低。

- **为什么这么定级**：触发窗口小（导入耗时通常毫秒级，用户恰好同时点开关的概率低），但修复成本几乎为零，且属于"数据悄悄错、用户毫无感知"的一类——静默丢更新比报错更糟。性价比极高的确定性修复。
- **一句话版本**：同一个文件的所有写入方必须排同一条队。
- **一个需要知道的取舍**：合并成单队列会让并发操作互相等待（用户体感"点了没反应"最长增加导入耗时）；但这正是正确性的代价，且各操作本来就都是毫秒级。
- **事故是怎么发生的**：用户导入一份备份，同时手快点了某插件"停用"→ 导入流程最后写补丁文件时用的是自己开始时读到的旧内容 → 用户的停用被无声回滚 → 用户以为停用了，实际插件仍在运行，直到出现他以为不可能发生的行为才暴露。

### P1-2 catalog.json 损坏被静默吞掉

**问题**：`readOverrides`（`src/index.ts:92`）对所有异常 `catch` 后返回空表：文件损坏（半截 JSON、BOM、编码错）时，用户自定义的所有中文名/说明**无声消失**，界面照常显示内置目录，没有任何"你的覆盖文件读不出来"的提示。用户的第一反应会是"我的备注被插件弄丢了"。

**建议**：`list()` 快照增加 `overridesWarning` 字段（读失败时携带错误摘要），界面在列表顶部渲染一条警告横幅："目录覆盖文件读取失败，已按出厂目录显示（文件：…；原因：…）"，并提供"把损坏文件改名保存"的一键操作。

**难度**：低。

- **为什么这么定级**：不丢真实数据（文件还在磁盘上），但用户**感知上**是数据丢了，且完全无提示、无自救入口——这正是"意想不到的操作要能被兜底"的反面教材。修复成本半天以内，用户困惑的代价却是持续的（每次打开都困惑一遍）。
- **一句话版本**：用户数据读不出来，必须喊出来，而不是装作没这回事。
- **一个需要知道的取舍**：横幅会在每次 list 都出现，可能让用户以为插件坏了；文案必须把"这是你的覆盖文件坏了，不是插件坏了，且内容还在磁盘上"讲清楚，否则会引来"插件弄丢我的数据"的误报。
- **事故是怎么发生的**：用户用带 BOM 的编辑器（或同步盘冲突副本）改了 catalog.json → 下次打开标签页，所有自定义备注消失 → 用户认定插件丢了数据，重新录入一遍（其实旧文件还在）→ 旧文件永未修复，问题反复出现。

### P1-3 备份导入"即选即写"，无预览无确认

**问题**：界面选择备份文件后直接调用 `importBackup`（`src/client/PluginManagerTab.tsx:291`），主机侧立即合并写入 catalog.json、profile package.json、补丁文件三个文件——没有预览要改什么，没有确认步骤。选错文件（旧机器的、别的 profile 的、内容过时的）时，启停状态和依赖会被批量合并进去，只有事后逐项排查才能发现。

**建议**：拆成两步：先"解析预览"（新增一个 dry-run 方法，返回将翻转的启停行、将新增/覆盖的依赖、将追加的备注清单），界面渲染成 diff 列表让用户确认后再真正执行。与 P0-3 的 spec 确认可以合并到同一个预览界面里。

**难度**：中（新主机方法 + 界面 diff 呈现；主机接口加一个方法，双宿主工件同步更新）。

- **为什么这么定级**：导入是"一次操作、三个文件、不可自动回退"的最重操作，却没有任何刹车。普通用户选错文件的场景非常现实：换机恢复、多 profile、多份历史备份并存。它是用户路径上的防呆缺口，不是理论风险。
- **一句话版本**：恢复操作必须先给用户看"将要改什么"，点头之后才动手。
- **一个需要知道的取舍**：预览与执行之间文件可能被别人改掉（预览的内容与实际写入不完全一致），严格做法是执行时按预览快照重验，但那会显著增加复杂度；务实的折中是预览时标明"基于 X 时刻的快照"，执行仍走合并语义（本来就不会删除条目，最坏情况是多合了一点）。
- **事故是怎么发生的**：用户三个月前导出过备份，当时为了排查问题停了一堆插件；今天随手把这份旧备份导回来想"恢复备注"→ 二十个启停行被合并翻转 → 会话行为变得诡异（工具没了、模型适配器没了），他完全想不起是这次导入干的。

### P1-4 启停可能被其它补丁层覆盖，UI 不解释

**问题**：`setEnabled` 只写全局层 `~/.dsh/cordis.patch.yml`。若同一行还被 profile 层补丁或其它层控制（层间优先级取决于宿主加载顺序），全局层的写入可能不生效或随后被覆盖。界面此时显示"已提交启停变更，正在热加载…"，900ms 后刷新发现状态没变，用户只得到一句静态提示（"如状态未变化，请点击刷新"），没有任何解释。

**建议**：最低成本版：toggle 后的刷新若发现 `enabled` 与请求相反，把卡片消息替换为"该插件的启停可能同时受 profile 层补丁控制，本次全局层修改未生效，请检查 <profile>/cordis.patch.yml"。进阶版：主机侧读 profile 层补丁，检测到同名行时在卡片上标注"受 profile 层控制"。

**难度**：中（低成本版低；进阶版需要宿主层信息，边界在宿主能力）。

- **为什么这么定级**：这是"功能正常但结果说不通"的典型——用户做了正确操作，得到的是错误世界的状态。会踩到的用户（多 profile、手工维护过多层补丁的进阶用户）恰恰是最依赖本插件的用户群。
- **一句话版本**：开关拨了没生效时，必须告诉用户"为什么没生效"，而不是让他自己猜。
- **一个需要知道的取舍**：主机侧检测其它层补丁要读 profile 目录的文件并理解层序——层序规则是宿主的内部约定，插件硬编码它会在宿主升级时悄悄失效；先做"检测到不生效就解释"的低成本版，把层序理解留给宿主，是更稳的边界。
- **事故是怎么发生的**：用户曾在 profile 层手工停用过某插件，后来在插件管家里点"启用"→ 全局层写入了 `disabled: false`，界面显示成功 → 实际 profile 层的 `disabled: true` 仍然生效 → 用户反复开关、重启、重装，最后留下一个 issue："插件管家的开关是坏的"。

### P1-5 与官方插件管理器的行 id 冲突无运行时检测

**问题**：本插件的 bundle 补丁与 DSH 0.2.0 官方 `@deepseek-ai/dsh-plugin-manager` 使用同一行 id `plugin-manager`，靠"后加载的 bundle 层胜出"实现替换（README 已注明）。这是宿主内部排序约定的依赖：宿主哪天调整加载顺序、改名行 id，替换就无声失效（官方管理器回来，或双份注册）。运行时没有任何检测。

**建议**：`list()` 里检测 loader 中是否存在 `@deepseek-ai/dsh-plugin-manager` 行及其 id；当两者并存且本插件行 id 与官方不一致时，在界面顶部渲染一条兼容性警告横幅（"本插件与官方插件管理器并存且未按预期接管，功能可能重叠"），同时在 CHANGELOG 里维护一份"已知兼容宿主版本"清单。

**难度**：中（检测逻辑简单；难点是定义"什么状态算异常"并让它不误报）。

- **为什么这么定级**：当前版本工作正常，但这是整个插件最大的单点兼容风险，且失效是静默的——用户不会报"替换没发生"，只会遇到两个管理器并存的怪现象。兼容性是本插件的生命线（它已经历 0.1.x → 0.2.0 两次适配），值得一个哨兵。
- **一句话版本**：依赖"后到者胜"这种宿主内部约定，就必须在运行时盯着它还成立。
- **一个需要知道的取舍**：横幅式警告只在用户打开标签页时可见；更彻底的方案（安装时校验宿主版本范围）需要在 bundle 补丁机制里加约束，那是宿主侧能力，插件自己做不到。先接受"打开才可见"的覆盖面。
- **事故是怎么发生的**：DSH 0.3.0 把 bundle 层加载顺序改成"官方行后置"→ 用户升级后官方插件管理器重新接管行 id → 两个管理器并存、启停行为互相打架 → 用户分不清哪个开关管用，而本插件对此毫无提示。

### P1-6 停用无撤销

**问题**：停用一个非系统插件是一键即达、无确认、无撤销的。对"非系统但重"的插件（如会话相关、压缩相关），误触会立刻改变当前会话的行为；用户需要记住停了什么、去列表里找回它。

**建议**：toggle 成功后在卡片消息区给出带"撤销"按钮的提示（8-10 秒内有效，超时自动收起）：撤销即对同一行再调一次 `setEnabled` 取反。利用现有 `scheduleReload` 的定时器机制承载即可，无需全局 toast 组件。

**难度**：低。

- **为什么这么定级**：系统行已保护、表达式行已标注，剩下的可停用插件里仍有"停了立刻难受"的一档；业界成熟模式是"危险操作不弹确认框、给可撤销窗口"（确认框打断高频正常操作，撤销不打断），本插件操作高频、列表长，撤销比确认更合适。
- **一句话版本**：误触的代价应该是一下"撤销"，而不是在 165 张卡片里回忆找卡。
- **一个需要知道的取舍**：撤销窗口内热加载已经真的发生了（浏览器半插件要刷新页面才完全卸载/回来），"撤销"恢复的是配置而不是瞬时状态——文案要写成"已撤销启停变更"而不是"已恢复原状"，避免用户误以为界面状态会瞬时回滚。
- **事故是怎么发生的**：用户在列表里快速滚动手滑点到"停用"（按钮紧挨卡片边缘）→ 正在跑的会话里某工具消失 → 他只看到一行绿色小字"已提交启停变更"，完全不知道刚才发生了什么、动了哪一行。

### P1-7 权限模型依赖宿主信任栅栏，暴露面未文档化

**问题**：六个网关方法（三个写文件）没有任何自有鉴权，安全性完全建立在"宿主 web-app 的信任栅栏挡住了非本机会话"这一假设上。用户如果把 web server 配置成监听非回环地址（宿主启动参数支持 host/port），任何能触达该端口的人都能翻转插件启停、改写配置文件。另外 `list()` 把两个文件的绝对路径返回给浏览器端展示，局域网会话可借此探知本机目录结构。这一切都没有在文档中说明。

**建议**：README 增加"安全模型"小节：明确"本插件不自带鉴权，启停/导入等写操作的可访问性完全由 DSH 的信任栅栏决定；不要在不受信网络中将 web server 暴露到非回环地址"。同时在设置页底部（现有 hint 区）加一行安全提示。能力允许的话，后续可评估宿主是否提供 per-service 权限声明。

**难度**：低（文档为主）。

- **为什么这么定级**：单机默认配置下风险是可控的（宿主栅栏兜底），所以不是 P0；但"权限管理机制"是评估目标明确要求的维度，而当前状态是"有隐式假设、无显式说明"——对一款公开发布、用户面在扩大的插件，安全假设必须写成文字，这是成本最低、收益最确定的安全动作。
- **一句话版本**：把"我安全是因为宿主帮我挡着"从心里的假设变成 README 里的一句话。
- **一个需要知道的取舍**：在插件层自建一套 token/确认机制会破坏"装完即用"的产品定位，且与宿主栅栏重复——文档化是当前正确的投入边界，真正的能力收敛（P3 级）应等宿主提供权限声明机制再做。
- **事故是怎么发生的**：用户在办公室想用手机访问 DSH，把 web server 监听改成 `0.0.0.0` → 同网段任何人打开页面即可改写他机器上的 `cordis.patch.yml` 与 profile 依赖（含 P0-3 所述的供应链路径）→ 事发后用户与作者都说不清"这插件到底有没有权限控制"。

### P2-1 toggle 后固定 900ms 单次刷新，状态可能滞后

**问题**：`AUTO_REFRESH_MS = 900`（`src/client/PluginManagerTab.tsx:88`）写死单次延时刷新，赌 HMR 在 900ms 内完成。重型插件、慢机器上会滞后，用户看到旧状态，只能按静态提示手动点刷新。

**建议**：改为轮询确认：刷新 2-3 次（如 300ms / 900ms / 2000ms），直到目标行的 `enabled` 与请求一致且 `fiberPhase` 回到稳态（active/failed/none）为止；或探测宿主是否暴露 loader 变更事件可订阅（进阶）。

**难度**：低-中。

- **为什么这么定级**：功能可用（有手动刷新兜底），但这是核心交互（启停）的体感问题，属于"每次都可能轻微不对，偶尔明显不对"的磨砂感；P1 里排不下它，但它比 P2 里其它项更值得先做。
- **一句话版本**：刷新不该赌一个固定毫秒数，该盯着结果确认到位。
- **一个需要知道的取舍**：轮询会增加 RPC 次数（每次 list 都同步读一次覆盖文件），高频轮询在低端机上反而是负担；三次封顶、命中即停是对的形状，不要做成无限重试。
- **事故是怎么发生的**：慢机器上 HMR 花了 1.5 秒 → 900ms 时刷新拿到旧状态 → 用户看到"停用"没生效，又点了一次"停用"（幂等，无害但困惑）→ 再点"启用"，两次操作在队列里排队后状态与预期相反 → 用户开始不信任这个开关。

### P2-2 remote.ts / typert-host.ts 全量重复 schema

**问题**：`src/client/remote.ts` 与 `src/typert-host.ts` 手工维护着两份几乎逐行相同的 zod schema（entry/snapshot/各 result/backup document，约 90 行 × 2）加一份相同的 `strictCodec`。改任何类型要同步两处，漏一处就是双宿主某一侧校验不一致，且这类漂移极难靠肉眼发现。

**建议**：抽出共享的 `src/schemas.ts`（schema + strictCodec），两个工件只保留各自的 descriptor/invocation 壳并从共享模块导入。两个文件本就是手写工件，共享模块不改变其"对齐 generator 输出形态"的性质。

**难度**：低。

- **为什么这么定级**：不修不影响任何当前行为，但每次类型演进（v0.8.0 必然会有）都是一次"改两处"的人为风险；DRY 债在双宿主这种高同步成本场景下利息最高，且修复是纯机械重构、有 e2e 钉着，风险接近零。
- **一句话版本**：同一份 schema 不该活在一个仓库的两个文件里。
- **一个需要知道的取舍**：共享后两个工件与"generator 输出形态"的字面相似度下降（文件里多了 import）——如果未来宿主要求工件"可逐字节比对 generator 输出"（目前没有这种要求），需要再拆回去；在 README 的开发节注明这一点。
- **事故是怎么发生的**：v0.8 给 `SetEnabledResult` 加了字段，作者改了 `remote.ts` 忘了 `typert-host.ts` → 浏览器端 strict codec 收到带新字段的结果正常、主机注册面却还是旧 schema（或反之）→ 某一代宿主上某个操作神秘失败，本地又测不出来（两份文件在作者机器上恰好都改了）。

### P2-3 无 ESLint、无 CI

**问题**：仓库没有任何 lint 配置、没有 `.github/`（无 CI）。测试和 typecheck 只在作者本机跑；README 承诺"双宿主验证"，但没有机制保证每次提交都被验证。catalog.ts 的机械生成部分（引号风格与手写部分不一致等）也无从约束。

**建议**：加 `eslint + typescript-eslint`（flat config，规则从宽）；加 GitHub Actions：push/PR 跑 `typecheck + test`（node 20/22 两个矩阵即可），一台机器、两分钟内能跑完。catalog 生成脚本若存在，顺手在 CI 里校验"生成产物与提交一致"。

**难度**：低。

- **为什么这么定级**：本插件的核心资产是"跨两代宿主仍然正确"，这恰恰最依赖每次提交都被自动验证；目前的双宿主 e2e 是手工跑的，依赖作者自觉。工程化缺失是所有"未来腐化"的放大器，但当前代码本身是干净的，所以排 P2 头部而非 P1。
- **一句话版本**：README 里承诺的兼容性验证，应该由 CI 替你兑现，而不是靠记得。
- **一个需要知道的取舍**：CI 只能覆盖 0.1.5-rc.3 / 0.2.0-rc.2 这两个钉死的版本集（devDependencies 决定），宿主 rc 持续演进时 CI 会给出"过时的绿灯"——需要配合一个"发版前手动对新 rc 跑一遍"的发版清单项，CI 无法替代这一步。
- **事故是怎么发生的**：某次重构改了 `patch-file.ts` 的行块匹配，本机忘了跑 `pnpm test` 就发布 → 用户安装后启停写坏补丁文件 → issue 进来时损坏已经随新版本扩散；如果当时有 CI，merge 前就被拦下。

### P2-4 浏览器半纯函数无测试

**问题**：5 个测试全部针对主机半；浏览器半的过滤/匹配/文案插值（`matches`、`format`、`dateStamp`，`src/client/PluginManagerTab.tsx:58-91`）与状态机逻辑（`ViewState`/`busy`/`messages`）零测试。React 组件级测试成本高，但纯函数完全可以低成本覆盖。

**建议**：把 `matches` / `format` / `dateStamp` 抽到 `src/client/util.ts`，用 `node:assert` 写一个 smoke（与现有测试同风格、零新依赖）；组件级测试等有 UI 回归需求再上 testing-library。

**难度**：低。

- **为什么这么定级**：当前纯函数逻辑简单到不太会错，直接风险低；但它们是搜索/过滤的用户可见行为，且抽取动作本身顺便降低组件体积。属于"顺手做"而非"必须做"。
- **一句话版本**：主机半测得再严，也遮不住浏览器半一行测试都没有的事实。
- **一个需要知道的取舍**：组件级测试（render + 交互）才能真正覆盖 toggle 状态机，但要引入 react testing 依赖链（jsdom 等），与"浏览器 bundle 零额外依赖"的洁癖有摩擦；先测纯函数、把组件测试的决策推迟到出现真实 UI 回归时。
- **事故是怎么发生的**：某次给搜索加了"按分类名匹配"，改坏了 `matches` 的空查询短路 → 空搜索框下列表不显示任何条目 → 因为没有测试且 e2e 不渲染浏览器半，发布后才被用户发现。

### P2-5 `file:` 安装的行显示名为原始路径

**问题**：模块名本身是 `file://` URL 的行（本地目录/文件方式加载的插件），`moduleShortName`（`src/catalog.ts:64`）不处理该形态，显示名直接是一整条 `file:///D:/.../noop.mjs` 原始路径——e2e 输出里实际出现：`"displayName":"file:///D:/.../noop.mjs"`。长路径挤占卡片标题行（title 悬浮可见但一眼读不到"这是哪个插件"）。

**建议**：`moduleShortName` 对 `file:` 前缀取 basename 去扩展名，并在卡片上加"本地"徽标；描述走现有兜底文案引导用户用"编辑备注"改名。

**难度**：低。

- **为什么这么定级**：纯显示问题，不丢数据不出错，但它是产品核心承诺（"每个插件都会自我介绍"）的直接违背——恰恰是本地开发者自装的插件最需要说明，却显示得最丑。开发者用户是本插件最早的传播者。
- **一句话版本**：本地路径安装的插件不该顶着一整条 file:// URL 过日子。
- **一个需要知道的取舍**：basename 可能重名（两个目录都叫 `my-plugin`），显示名撞车；徽标 + 完整 moduleName 仍在卡片上（`<code>` 行）可区分，不用为此引入更复杂的去重逻辑。
- **事故是怎么发生的**：开发者用 `file:` 方式试装自己的插件 → 标签页里出现一行 `file:///C:/Users/.../dist/index.js` → 截图发到社区"这插件怎么显示乱码路径"，第一印象受损。

### P2-6 restoreNoChange 死分支 + 全 0 计数文案

**问题**：`importBackup` 成功时恒返回 `detail`（`src/index.ts:460`），界面里 `detail === undefined` 走 `restoreNoChange` 文案的分支（`src/client/PluginManagerTab.tsx:306`）永远不可达；零变更的导入显示"恢复完成：备注 0 条、依赖 0 个、插件 0 个、启停 0 行"——字面上像出了问题，实际是"什么都不用改"。

**建议**：界面判断四个计数全为 0 时改用 `restoreNoChange`（"备份内容已全部就位，无需变更"）；顺手删除死分支或修正条件。

**难度**：低。

- **为什么这么定级**：已有的文案和逻辑都写好了，只是条件接错了线——修复是五行内的改动；但它出现在"备份与恢复"这个用户最敏感的区域，全 0 的"恢复完成"足以让用户怀疑操作失败。
- **一句话版本**："什么都没改"和"改完了"必须说成两句话。
- **一个需要知道的取舍**：`patchRowsRestored` 等计数语义是"本次实际变更数"，未来若与 P1-3 的预览合并，这个判断条件要跟着预览数据走，不要在这次小修里过度设计。
- **事故是怎么发生的**：用户重复导入同一份备份（想确认恢复成功）→ 看到"恢复完成：0 条、0 个、0 个、0 行"→ 以为恢复失败，又导了一次，然后开始担心备份文件坏了，来提 issue。

### P2-7 CATEGORY_LABELS 两处重复

**问题**：分类中文标签在主机 `src/catalog.ts:20` 与浏览器 `src/client/PluginManagerTab.tsx:42` 各维护一份，靠人肉同步；新增分类时漏改一侧，界面就会出现"分类下拉里是中文、卡片徽标里是英文 key"（或反之）的不一致。

**建议**：分类标签随 `list()` 快照下发（快照加一个 `categoryLabels` 字段），或浏览器直接 `import` 主机 catalog 里的常量（相对路径导入，不违反 bundle 纯度守卫）。推荐前者——目录数据本来就该由目录方提供。

**难度**：低。

- **为什么这么定级**：与 P2-2 同类（双份维护），但影响面更小（分类 rarely 变）；单独列出让它在排期时不占用 P1 资源，随手可修。
- **一句话版本**：分类叫什么名字，该由目录一个地方说了算。
- **一个需要知道的取舍**：随快照下发给快照 schema 加字段，双宿主工件与 e2e 断言都要动；直接 import 则零接口变化但要往浏览器 bundle 里带进整个 catalog 常量（几十 KB 内，可接受）。两者都可，别两个都做。
- **事故是怎么发生的**：v0.8 新增 `mcp` 分类 → 主机侧加了标签、浏览器侧漏了 → 用户界面下拉框里出现一行裸英文 `mcp`，卡片徽标却是中文——同一屏两种语言，反馈"插件是不是坏了"。

### P2-8 服务端无输入长度上限；恢复计数虚高

**问题**：三个写方法对输入只做非空校验：`setOverride` 的 name/desc 无服务端长度上限（客户端 maxLength 60/200 可绕过），`importBackup` 的 json 无大小上限；一次调用可以往 catalog.json 写入兆级字符串。另外 `mergeOverrides`（`src/backup.ts:100`）对每条 incoming 无条件 `changed += 1`，与内容相同也计数，恢复文案可能虚报。

**建议**：服务端给 name/desc 各 200/1000 上限（超限返回 `invalid-input` 与明确文案）、给 json 一个上限（如 2MB，超限提示"备份文件过大"）；`mergeOverrides` 比对当前值后再计数。

**难度**：低。

- **为什么这么定级**：这些是自我 DoS / 文案失真级别的健壮性问题（调用方是本插件自己的界面，恶意调用需先突破宿主栅栏），所以到不了 P1；但修复是纯防御性几行代码，与 P0-3 的 json 上限天然是同一处改动，合并实施。
- **一句话版本**：客户端的限制只是礼貌，服务端的限制才是限制。
- **一个需要知道的取舍**：上限会拒绝极端合法输入（用户真的写了 1000 字的插件说明）——上限放宽到"显然异常才拦"的量级（desc 1000 字），并把错误文案写明限制值，让被拒用户能自助。
- **事故是怎么发生的**：用户用"编辑备注"粘贴了一整篇插件评测进说明字段（客户端 200 字限制拦截不了旧版界面/其它调用方）→ catalog.json 膨胀、卡片渲染超长 → 恢复文案还把这条计成"1 条"，用户更困惑。

### P2-9 英文界面下目录内容仍是中文

**问题**：内置目录的名字与说明只有中文（`src/catalog.ts`），英文 locale 下界面文案全英文，但每张卡片仍显示"定时器服务"等中文名与中文说明——对英文用户，本插件的核心价值（可读的说明）不可用，还显得未完成。

**建议**：目录条目结构加可选 `nameEn` / `descEn`；英文环境优先取英文字段，缺失时回退到模块短名 + 英文兜底说明（而不是中文说明）。内置目录可先只给高流量条目补英文，长尾跟随社区贡献。

**难度**：低-中（数据结构小改 + 165 条的英文文案工作量是大头）。

- **为什么这么定级**：README 有 7 种语言版本、社区面向国际（Awesome 收录），但产品核心内容只服务中文用户——不一致会被英文用户第一时间感知；不过英文用户当前占比与痛点强度有限，且文案工作量大，不适合排进 P1。
- **一句话版本**：7 种语言的 README 配一份只有中文的目录，英文用户看到的仍是一个"中文插件"。
- **一个需要知道的取舍**：回退到"短名 + 兜底说明"会让英文用户的卡片比现在更"空"（现在至少有中文可猜）；要接受"英文下信息密度暂时下降"换取"不再出现中英混排"，并给编辑备注功能一个明显的入口让用户自填英文。
- **事故是怎么发生的**：海外用户按英文 README 装好插件 → 界面里"热加载驱动""会话存储核心"扑面而来 → 第一条 issue："Is this plugin Chinese-only?"，README 的多语言承诺反而放大了落差。

### P3-1 启停审计日志

**问题/提案**：所有启停/导入只留"结果"，不留"历史"。排查"环境什么时候变坏的"时没有时间线可查。
**建议**：主机侧把每次写操作（动作、行 id、旧值→新值、来源、时间）追加到 `~/.dsh/plugin-manager/history.jsonl`（有界滚动，如最近 500 条）；界面可在卡片或页脚提供"最近变更"入口。
**难度**：低-中。

- **为什么这么定级**：价值真实（本插件管理的正是"会突然改变行为"的东西），但不解决现有缺陷，属于增益功能；放 P3 等核心防呆（P0/P1）落地后再做。
- **一句话版本**：给每一次启停留一行"谁在什么时候把什么改成了什么"。
- **一个需要知道的取舍**：日志文件无限增长与隐私（记录了用户的插件使用轨迹）之间的平衡需要滚动清理策略；日志本身也可能像 catalog.json 一样损坏，写入要走 P0-1 的原子写。
- **事故是怎么发生的**：用户隔周发现某个插件不工作了，但他不记得自己上周停过什么、也不知道是不是某次导入干的——没有日志，只能凭记忆与猜测。

---

### P3-2 分组/层级展示

**问题/提案**：`list()` 跳过分组行，用户看不到行之间的 include/分组从属关系（entryId 里的 `include:` 前缀是唯一线索），对"这个行 id 为什么长这样"缺少解释。
**建议**：快照给每行附父分组名，界面按分组折叠展示或至少在 meta 行显示"属于：分组 X"。
**难度**：中。

- **为什么这么定级**：进阶信息，新手用不到；但它直接关联 P1-4（层与行 id 的困惑），做了它能顺带解释很多"行 id 怪现象"。等 P1-4 反馈积累后再决定投入。
- **一句话版本**：把"行从哪儿来"显示出来，行 id 就不再是天书。
- **一个需要知道的取舍**：分组视图会让 165 张卡片的浏览路径变长（多一层折叠）；需要保留平铺 + 搜索作为默认，分组只作为可选视图。
- **事故是怎么发生的**：用户看到 `include:xxx` 前缀的行 id，以为是两个独立插件，停用了"看起来重复"的那个，实际拆散了一组配置。

### P3-3 批量启停（带确认）

**问题/提案**：165 个插件逐个开关，"停用所有第三方插件排查冲突"这类真实诉求要点击几十次。
**建议**：支持按分类/搜索结果多选批量启停；必须经过强确认（显示将影响 N 行的清单，二次点击确认），系统行自动排除。
**难度**：中。

- **为什么这么定级**：真实的高频排障场景（社区插件冲突排查），但批量误操作的风险远高于单次（一次坏 20 个插件的行为），必须有成熟的确认与撤销（依赖 P1-6）垫底才安全。
- **一句话版本**：批量开关是排查冲突的刚需，但必须配一道重重的确认门。
- **一个需要知道的取舍**：批量停用后热加载风暴（20 行同时翻转）可能让宿主短暂卡顿；批量操作可以选择"逐行应用 + 间隔"以平滑，代价是总耗时变长。
- **事故是怎么发生的**：用户多选时框选范围多勾了两个会话核心插件（不在系统清单里但很关键）→ 一键停用 → 正在跑的会话全部异常，且他要靠记忆恢复。

---

### P3-4 插件健康视图（failed 置顶）

**问题/提案**：fiber `failed` 的行目前只是一个红点埋在 165 张卡片里，没有集中视图；"哪个插件挂了"要靠肉眼扫。
**建议**：页首增加状态摘要条（"N 个插件挂载失败"可点击过滤），failed 行排前并尽量展示失败原因（若宿主 loader 能暴露）。
**难度**：中（界面部分低；拿失败原因是宿主能力边界）。

- **为什么这么定级**：明确有用的运维向增强，但当前红点 + 搜索已能用；失败原因的获取受宿主暴露面限制，投入前应先确认宿主给不给数据。
- **一句话版本**：挂了的插件不该靠用户在长列表里找红点。
- **一个需要知道的取舍**：只做"过滤 failed"很简单，但用户真正想要的是"为什么 failed"——如果宿主不给原因，做了过滤也只是把绝望集中展示；建议把它与宿主能力调研绑定立项。
- **事故是怎么发生的**：用户装了新插件后其它插件静默挂载失败，他只觉得"某些功能没了"，在列表里翻了半天才发现那个红点。

### P3-5 拼音搜索 / 排序控制

**问题/提案**：搜索只匹配子串，中文用户无法用拼音首字母（如 `hc` 找"热加载驱动"）；列表无排序选项。
**建议**：给目录条目加可选拼音索引字段（内置目录静态生成即可，无需运行时转换库）；排序先做"启用优先 / 名称"两档。
**难度**：低。

- **为什么这么定级**：锦上添花的搜索增强，当前子串搜索（可搜中文本身）已覆盖主要场景；拼音数据又是一份要维护的重复数据（与 P2-7 同病），不急。
- **一句话版本**：会打中文的人不缺这次搜索，不会打中文的人才需要拼音——先确认后者真实存在。
- **一个需要知道的取舍**：静态拼音索引只覆盖内置目录，用户自定义备注搜不到拼音（除非引入运行时转换库，那是几 MB 的依赖）；半吊子拼音搜索可能比没有更让人困惑，需在占位文案里写明"支持拼音首字母（内置目录）"。
- **事故是怎么发生的**：——此项无事故，属于体验打磨；若要写一条，就是用户记不住英文名也懒得切输入法，索性不用搜索靠肉眼翻。

### P3-6 一键恢复出厂（清理本插件写入的行）

**问题/提案**：本插件往补丁文件写入的行没有标记，"让补丁文件回到插件未介入的状态"只能手工逐行删。
**建议**：写入的行块加注释标记（`# by plugin-manager`），提供"清理本插件管理的行"操作（逐行确认后移除）；无法识别标记的历史行不动。
**难度**：中。

- **为什么这么定级**：兜底逃生门，平时没人用、出事时极其有用（尤其配合 P1-4 的层混乱场景）；但行注释标记会改变补丁文件的"手术式最小改动"美学，且旧版本写入的行没有标记、覆盖不全，恢复出厂永远只能做到"尽力而为"。
- **一句话版本**：插件往用户配置里写的东西，应该带着签名，并能一键收回。
- **一个需要知道的取舍**：带标记的注释会让手工编辑的用户看到"多余"的行，也考验 patch-file 解析的稳定性（注释必须严格保留原样）；更简单的替代是只提供"把当前补丁文件完整备份为 .bak"而不做智能清理。
- **事故是怎么发生的**：用户想完全卸载本插件 → README 让他"手工清理 cordis.patch.yml 里的行"→ 他分不清哪些行是插件写的、哪些是自己手工加的 → 删错行，别的插件配置损坏。

---

### P3-7 catalog.json 无版本字段

**问题/提案**：覆盖文件是裸对象（模块名 → 字段），无格式版本；未来若扩展字段（英文备注、排序偏好），没有升级路径可区分新旧文件。
**建议**：下次需要破坏性扩展时一并引入版本包装（`{ version: 1, overrides: {...} }`），读取时兼容裸对象旧形态；在此之前不动（避免无意义的迁移）。
**难度**：低。

- **为什么这么定级**：纯前瞻性设计，当前单一形态没有歧义；提前引入版本字段是过度设计。原则：版本字段应该在实际需要兼容第二种形态的前一个版本引入。
- **一句话版本**：现在不用加，但下次要动覆盖文件结构时，第一步先加版本号。
- **一个需要知道的取舍**：加了版本字段，所有读写路径都要多一层拆包/兼容逻辑，且备份文档的 overrides 形态要不要跟着变（版本耦合）需要决策；收益只在"未来某天"，成本是现在。
- **事故是怎么发生的**：v1.0 给覆盖加新字段后，老用户的裸对象文件被新版读出半截（或新版写出的文件被老版读崩），且没有版本号能判断这是谁的文件——那时想加版本号已经晚了。

---

### P3-8 虚拟化与读缓存

**问题/提案**：当前规模（165 行、文件 KB 级）性能没有任何问题：`list()` O(n)、每次同步读一个小 JSON、搜索全量 re-render 都在毫秒级。若未来目录/插件数量增长一个数量级，卡片列表需要虚拟化，`readOverrides` 需要 mtime 缓存。
**建议**：现在不做；设一个复核触发点（entryCount > 500 或单次 list 耗时 > 50ms 时再立项）。
**难度**：中。

- **为什么这么定级**：评估目标点名了"性能效率/响应速度"，诚实的结论是当前没有性能问题；把"不做"写成一条有触发条件的决策，好过假装它不存在或在数据全无压力时引入虚拟化的复杂度。
- **一句话版本**：165 个插件没有性能问题，别为了"可能有一千个"提前付复杂度。
- **一个需要知道的取舍**：虚拟化会破坏"Ctrl+F 浏览器内查找"与无障碍的整页语义（需要额外的 aria 处理）；在需要它之前引入它是净损失。
- **事故是怎么发生的**：不会发生——这正是把它放在 P3 末尾的原因；唯一的"事故"是有人提前做了它，让一次简单的启停改动变成一次渲染层重构。

## 5. 不建议现在做的事

- **插件层自建鉴权体系**：与宿主信任栅栏重复且破坏"装完即用"；先做 P1-7 文档化，等宿主提供权限声明机制。
- **覆盖文件结构升级**：见 P3-7，等真实需求。

- **运行时拼音转换库**：见 P3-5，依赖体积与收益不成比例。
- **catalog 大规模扩容（如社区共建收录流程）**：目录条目已达 165+，人工维护接近上限；应先解决 P2-7/P3-7 的数据治理，再谈扩容机制。
